# 주식 데이터 수집 프로그램 개발 명세서 v1

Nov 18, 2026 · @김선범

## 1. 목적과 범위

이 프로그램은 **국내 주식 데이터를 수집·저장하고, 브리핑용 파일 하나로 묶어 내보내는 로컬 도구**입니다. 매수·매도 판단, 점수 매기기, 브리핑 글 작성은 하지 않습니다. 판단은 사용자가 Claude에 파일을 넘겨 따로 진행합니다.

**0단계 실측 결과로 바뀐 내용은 14장에 있습니다. 앞 장과 내용이 다르면 14장이 우선합니다.**

| 구분 | 포함 | 제외 |
| --- | --- | --- |
| 수집 | KRX 시세·지수·종목정보, KIS 수급·휴장일·종목기본, DART 재무·공시목록 | 뉴스, 컨센서스, 분봉·호가, NXT 시세 |
| 가공 | 기간 합계·수익률·증가 배수 같은 **판단 없는 요약 계산** | 강세·약세 판정, 점수, 순위 확정 |
| 출력 | 브리핑 패키지 파일(KRX+KIS), DART 구글 시트용 CSV | 화면(UI), 차트, 브리핑 글 |
| 실행 | 사용자가 장 마감 후 직접 실행 | 자동 예약 실행, 자동 주문 |
| 기타 | 테마 마스터 CSV 읽기 | 보유 종목 관리 (별도 대화에서 운영) |

**기준값**

| 항목 | 값 |
| --- | --- |
| 대상 시장 | KRX 코스피·코스닥 (NXT·통합 자료는 받지 않음) |
| 대상 종목 | 보통주. 스팩·리츠·ETF·ETN·우선주 제외 |
| 시세·지수 보관 기간 | 250거래일 |
| 수급·공시목록 보관 기간 | 120거래일 |
| 재무 보관 기간 | 3년 (12분기) |
| 기본 단위 | 일봉, 거래일 |

## 2. 실행 환경과 이식성

**Windows 10/11에서 Python 3.12로 동작하고, 같은 코드가 macOS에서도 돌아가게 만듭니다.** 어느 PC에서 새로 설치해도 이전 상태에 기대지 않고 처음부터 스스로 준비하는 것이 원칙입니다.

### 2.1 기술 스택

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 언어 | Python 3.12 | KIS 공식 예제가 Python, Windows·Mac 공통 |
| 저장소 | SQLite (파일 1개) | 서버 설치 불필요, 폴더 복사만으로 이동 가능 |
| HTTP | httpx | 재시도·타임아웃 제어 |
| 표 처리·내보내기 | pandas, openpyxl | 브리핑 패키지 xlsx 생성 |
| 설정 | python-dotenv | API 키를 코드 밖에 보관 |
| 화면 | 터미널 번호 메뉴 + 명령줄 인자 | 수동 실행에 충분, UI 개발 불필요 |
| 실행 파일 | Windows 실행 파일 `주식데이터수집기.exe` (2.5 참고). Mac은 코드로 직접 실행 | 더블클릭으로 메뉴 실행 |

### 2.2 실행 메뉴

1. 당일 수집 (KRX+KIS, 빠진 날짜 자동 보충)
2. 기간 수집 (시작일·종료일 입력)
3. 브리핑 패키지 생성 (기준일 입력, 기본값 = 마지막 수집일)
4. DART 수집 (주간·월간 실행용)
5. DART 구글 시트용 내보내기
6. 상태 점검 (키 유효성, 마지막 수집일, 빈 날짜, 재확인 필요 항목)
7. 실측 검증 (최초 1회, 12장 참고)

같은 기능을 `python -m collector daily`, `python -m collector range --from 20260601 --to 20261118`처럼 명령줄로도 실행할 수 있어야 합니다. 나중에 AI API를 붙일 때 이 명령을 그대로 부르기 위해서입니다.

exe도 같은 인자를 받습니다. 예: `주식데이터수집기.exe daily`. 인자 없이 더블클릭하면 메뉴가 뜹니다.

### 2.3 어느 PC에서나 새로 실행되기 위한 규칙

| 규칙 | 내용 |
| --- | --- |
| 상태 저장 위치 | 프로그램 폴더와 데이터 폴더 두 곳만 사용. 레지스트리, 시스템 환경변수, 다른 경로에 아무것도 쓰지 않음 |
| 절대 경로 금지 | 코드·설정·DB 어디에도 `C:\Users\이름\...` 같은 경로를 저장하지 않음. 데이터 폴더 안 경로는 항상 상대 경로 |
| 시작 시 자가 점검 | 실행할 때마다 폴더 생성 → DB 없으면 새로 만들기 → DB 스키마 버전 확인·업그레이드 → 무결성 검사 순서로 진행 |
| 수집 여부 판단 | 오직 데이터 폴더의 DB 기록으로만 판단. 데이터 폴더를 통째로 다른 PC에 복사하면 이어서 쓰고, 없으면 처음부터 수집 |
| 중복 실행 방지 | 실행 중 잠금 파일을 만들고, 남아 있는 잠금 파일은 해당 프로세스가 죽었으면 자동 해제 |
| 중단 후 재실행 | 모든 저장은 단위별 트랜잭션. 강제 종료 후 다시 실행하면 끝난 곳 다음부터 이어서 진행 |
| KIS 토큰 | 데이터 폴더에 만료 시각과 함께 캐시. 없거나 만료되면 새로 발급. 접근 토큰은 하루 유효하고 발급은 1분에 1회로 제한되므로 매 실행마다 재발급하지 않음 ([wikidocs](https://wikidocs.net/453548)) |
| 시간대 | 모든 날짜·시각은 PC 설정과 무관하게 Asia/Seoul 기준으로 계산 |

### 2.4 API 키 보관

- 키는 \*\*프로그램 설치 폴더 안의 `secret/keys.env`\*\*에 둡니다. 데이터 폴더(바탕화면)에는 두지 않습니다. 바탕화면은 OneDrive 동기화 대상인 경우가 많아, 키가 클라우드로 퍼질 수 있습니다.
- **업데이트해도 키가 유지되어야 합니다.** 새 버전을 덮어쓰어 설치할 때 설치 과정(또는 압축 배포본)은 `secret/` 폴더를 만들거나 지우거나 덮어쓰지 않습니다. 배포본에는 `secret/` 폴더를 아예 포함하지 않고, 프로그램이 실행될 때 없으면 새로 만듭니다.
- 처음 실행했는데 `secret/keys.env`가 없으면 키를 하나씩 입력받아 저장합니다. 필요한 키는 `KRX_AUTH_KEY`, `KIS_APP_KEY`, `KIS_APP_SECRET`, `DART_API_KEY`입니다. 키가 틀렸을 때 다시 입력하는 메뉴도 상태 점검에 둡니다.
- `DATA_DIR` 같은 일반 설정은 키와 분리해 설치 폴더의 `config/settings.env`에 둡니다. 이 파일도 업데이트 때 덮어쓰지 않고, 새 버전에 새 설정 항목이 생기면 기본값만 덧붙입니다.
- 키 값은 로그·화면·브리핑 파일 어디에도 출력하지 않습니다. 필요하면 앞 4자리만 표시합니다.

### 2.5 개발·빌드·설치 방식

**코드는 클라우드에서 개발하고, Windows 실행 파일(.exe)을 받아 PC에 설치해 실행합니다.** PC에는 Python을 설치하지 않습니다.

| 단계 | 어디서 | 방법 |
| --- | --- | --- |
| 개발 | 클라우드 | 웹 버전 Claude Code가 GitHub 비공개 저장소의 코드를 수정. 어느 기기의 브라우저에서든 이어서 작업 |
| 빌드 | GitHub Actions (Windows 서버) | 버전 태그(예: `v0.3.0`)를 붙이면 PyInstaller로 exe를 만들어 GitHub Releases에 zip으로 올림. 수집에는 쓰지 않고 빌드에만 사용 |
| 설치 | PC | Releases에서 zip을 받아 고정 위치(예: `C:\주식데이터수집기\`)에 풀고 exe 실행 |
| 업데이트 | PC | 새 zip을 같은 위치에 덮어쓰기. `secret/`, `config/settings.env`는 zip에 들어 있지 않아 그대로 유지 |
| 데이터 | PC | 바탕화면 `주식데이터수집` 폴더 (3장). GitHub에는 올리지 않음 |

**빌드 규칙**

- PyInstaller는 파일 하나로 묶는 `--onefile` 대신 폴더 형태(`--onedir`)로 빌드합니다. 실행이 빠르고 백신 프로그램의 오진이 줄어드는 쪽입니다.
- exe에 버전 번호를 넣고, 실행 로그와 브리핑 패키지 `0_안내` 시트에 기록합니다.
- 빌드 작업에는 API 키가 필요 없습니다. GitHub Secrets에 키를 넣지 않습니다.
- 서명되지 않은 exe라서 처음 실행할 때 Windows가 "PC 보호" 경고를 띄울 수 있습니다. README에 "추가 정보 → 실행" 절차를 적습니다.

**개발 환경의 한계:** 웹 버전 Claude Code는 Linux에서 작업합니다. 바탕화면 경로 찾기, 한글 경로, exe 실행처럼 Windows에서만 일어나는 동작은 개발 중에 시험할 수 없습니다. 그래서 이런 코드는 OS별로 분리하고, Linux에서는 대체 동작으로 테스트한 뒤 PC에서 exe로 최종 확인합니다. 실측 검증(12장)에서 필요한 실제 API 호출도 PC에서 exe로 실행합니다. 클라우드 개발 환경에는 API 키를 넣지 않기 위해서입니다.

## 3. 폴더 구조와 파일 규칙

**데이터는 바탕화면의 `주식데이터수집` 폴더에 저장하고, 모든 산출 파일의 이름에 기준일과 생성 시각을 넣습니다.** 폴더가 없으면 프로그램이 실행될 때 자동으로 만듭니다.

### 3.1 바탕화면 경로 찾기

| OS | 방법 |
| --- | --- |
| Windows | `C:\Users\이름\Desktop`을 직접 적지 않고, Windows API(`SHGetKnownFolderPath`, `FOLDERID_Desktop`)로 실제 바탕화면 경로를 얻음. OneDrive로 옮겨진 바탕화면(`OneDrive\바탕 화면`)도 이 방법으로만 정확히 잡힘 |
| macOS | `~/Desktop` |
| 수동 지정 | `.env`의 `DATA_DIR`에 경로가 있으면 그 경로를 우선 사용 |

**주의: 바탕화면이 OneDrive 동기화 폴더인 경우.** 실행 중인 SQLite DB를 클라우드 동기화가 건드리면 파일이 손상될 수 있습니다. 그래서 바탕화면 경로에 `OneDrive`가 포함되면 시작할 때 경고를 띄우고, `DATA_DIR`로 동기화되지 않는 경로를 지정하라고 안내합니다. 백업은 11장의 DB 스냅샷으로 대신합니다.

### 3.2 폴더 구조

```
주식데이터수집/
├─ db/
│   └─ market.sqlite              ← 정제 데이터 전체 (수집 여부 판단의 유일한 기준)
├─ raw/                           ← API 원본 응답 (가공 전 그대로)
│   ├─ krx/2026-11/
│   ├─ kis/2026-11/
│   └─ dart/2026-11/
├─ briefing/                      ← 브리핑 패키지 (Claude에 올릴 파일)
├─ dart_export/                   ← 구글 시트용 DART CSV
├─ themes/
│   ├─ theme_master.csv           ← 현재 사용 중인 테마 목록 (사용자가 편집)
│   └─ history/                   ← 수정 전 버전 자동 보관
├─ logs/                          ← 실행 로그
├─ backup/                        ← DB 스냅샷
└─ system/                        ← 토큰 캐시, 휴장일 캐시, 잠금 파일 (사용자가 열 필요 없음)
```

### 3.3 파일명 규칙

파일명에는 **두 가지 날짜를 구분해서** 넣습니다. 데이터가 언제 것인지(기준일)와 파일을 언제 만들었는지(생성 시각)는 다르기 때문입니다. 예를 들어 금요일 장을 월요일에 수집하면 두 날짜가 달라집니다.

형식: `{출처}_{데이터}_{기준일 또는 기간}_{생성 YYYYMMDD-HHMMSS}.{확장자}`

| 파일 | 예시 |
| --- | --- |
| KRX 원본 | `krx_stk_daily_20261118_20261118-183512.json.gz` |
| KIS 수급 원본 (한 번 실행분을 한 파일로) | `kis_investor_20261118_20261118-183640.jsonl.gz` |
| 브리핑 패키지 | `briefing_20261118_20261118-190205.xlsx` |
| DART 내보내기 | `dart_financials_2023Q4-2026Q3_20261122-101500.csv` |
| 로그 | `run_20261118-183500.log` |
| DB 스냅샷 | `market_20261118-190300.sqlite` |

- 같은 기준일로 여러 번 만들어도 생성 시각이 달라 기존 파일을 덮어쓰지 않습니다.
- **파일명은 기록용이며, 수집 여부를 판단하는 데 쓰지 않습니다.** 판단은 DB의 수집 기록(7장 `collect_log`)로만 합니다.
- DB 파일 자체는 고정 이름(`market.sqlite`)을 씁니다. 날짜가 붙은 사본은 `backup/`에 만듭니다.
- 원본 파일은 월별 폴더로 나누고 gzip으로 압축합니다. KIS 수급은 하루 약 2,500회 호출되므로 호출마다 파일을 만들지 않고, 한 번의 실행을 한 파일에 줄 단위로 쌓습니다.

## 4. 데이터 출처와 API 목록

**시세·지수·종목정보는 KRX 날짜별 조회, 수급은 KIS 종목별 조회, 재무·공시는 DART에서 받습니다.** 같은 항목을 두 출처에서 받을 수 있어도 기본 출처는 하나로 고정하고, 다른 출처는 교차 확인용으로만 씁니다. KRX 서비스는 모두 이용 승인 상태입니다.

### 4.1 KRX Open API

| 서비스 | 경로 | 조회 단위 | 주요 필드 | 용도 |
| --- | --- | --- | --- | --- |
| 유가증권 일별매매정보 | `/sto/stk_bydd_trd` | `basDd` 날짜 1개 → 코스피 전 종목 | 시가·고가·저가·종가, 거래량 `ACC_TRDVOL`, 거래대금 `ACC_TRDVAL`, 시가총액 `MKTCAP`, 상장주식수 `LIST_SHRS` | 일봉의 **기본 출처** |
| 코스닥 일별매매정보 | `/sto/ksq_bydd_trd` | 위와 같음 (코스닥) | 위와 같음 | 위와 같음 |
| 유가증권 종목기본정보 | `/sto/stk_isu_base_info` | 날짜 1개 → 전 종목 | 상장일 `LIST_DD`, 증권구분 `SECUGRP_NM`, 소속부 `SECT_TP_NM`, 주식종류 `KIND_STKCERT_TP_NM` | 대상 종목 필터, 신규 상장 |
| 코스닥 종목기본정보 | `/sto/ksq_isu_base_info` | 위와 같음 | 위와 같음 | 위와 같음 |
| KOSPI 시리즈 일별시세정보 | KRX 서비스 상세 페이지에서 확인 | 날짜 1개 → 시리즈 전체 지수 | 지수명, 종가, 등락률, 거래량·거래대금 | 시장 전체 흐름 기준 |
| KOSDAQ 시리즈 일별시세정보 | 위와 같음 | 위와 같음 | 위와 같음 | 위와 같음 |

필드명은 공개된 클라이언트 코드 기준입니다 ([매매정보](https://glama.ai/mcp/servers/@jjlabsio/korea-stock-mcp/blob/81fe2726c81d1ceb4da58abf17bbb2c46dae388f/src/krx/get-trade-info.ts), [기본정보](https://glama.ai/mcp/servers/@jjlabsio/korea-stock-mcp/blob/81fe2726c81d1ceb4da58abf17bbb2c46dae388f/src/krx/get-base-info.ts)). 실측 검증(12장)에서 실제 응답과 대조합니다.

아래 API는 모두 **모의투자 미지원**입니다. 도메인은 `https://openapi.koreainvestment.com:9443`, 고객 타입은 `P`(개인)입니다.

KIS 문서는 당일 데이터가 15:40 이후 가집계되어 그때부터 조회 가능하고 산출 시간은 일정하지 않다고 적으면서, 동시에 "00:00\~15:40 이외의 시간은 당일 조회가 제한"된다고도 적어 서로 모순됩니다. 실측으로 확인합니다.

## 5. 대상 종목 필터와 신규 상장 인덱스

**코스피·코스닥 보통주만 남기고, 스팩·리츠는 두 가지 이상의 근거로 제외합니다.** 제외한 종목도 삭제하지 않고 제외 사유와 함께 DB에 남깁니다. 필터가 잘못됐을 때 되돌릴 수 있게 하기 위해서입니다.

### 5.1 필터 규칙 (위에서부터 순서대로 적용)

| 순서 | 조건 | 근거 필드 | 결과 |
| --- | --- | --- | --- |
| 1 | 코스피·코스닥이 아님 (코넥스 등) | KRX 시장구분 | 제외: `market` |
| 2 | 보통주가 아님 (우선주 등) | KRX `KIND_STKCERT_TP_NM`, KIS `stck_kind_cd` ≠ `101` | 제외: `not_common` |
| 3 | 주권이 아님 (ETF·ETN·리츠·외국주권·DR 등) | KIS `scty_grp_id_cd` ≠ `ST` (예: `RT` 부동산투자회사, `EF` ETF), KRX `SECUGRP_NM` | 제외: `not_stock` (리츠는 `reits`) |
| 4 | 스팩 | KRX `SECT_TP_NM`의 스팩 표기(실측 확인 후 확정) **또는** 종목명에 `스팩` 포함 | 제외: `spac` |
| 5 | 위 어느 것에도 해당 없음 |  | 분석 대상 |

- KRX와 KIS의 판단이 엇갈리면 **제외하지 않고** `filter_conflict`로 표시합니다. 상태 점검 메뉴에서 목록을 보여주고, 사용자가 확인한 뒤 확정합니다.
- 스팩은 KIS 증권그룹 코드에 별도 항목이 없어 일반 주권(`ST`)으로 분류될 가능성이 높습니다. 그래서 종목명 규칙을 항상 함께 적용합니다.
- 관리종목·거래정지는 **제외하지 않고 표시만** 합니다(`is_admin`, `is_halted`). 브리핑에서 어떻게 다룰지는 판단 단계의 문제입니다.
- 필터는 매일 다시 계산하고, 날짜별로 기록합니다. 상장폐지된 종목도 폐지 전 날짜의 기록은 그대로 남습니다.

### 5.2 신규 상장 인덱스

모든 분석 대상 종목에 대해 매일 아래 값을 계산해 저장하고, 브리핑 패키지에도 그대로 넣습니다.

| 필드 | 의미 | 계산 |
| --- | --- | --- |
| `listed_date` | 상장일 | KRX `LIST_DD` |
| `days_since_listing` | 상장 후 거래일 수 (상장일 = 1) | 거래일 달력으로 셈. 달력 날짜로 세지 않음 |
| `is_new_listing` | 신규 상장 여부 | `days_since_listing` < 60 |
| `max_window` | 계산 가능한 가장 긴 관찰 기간 | 5 / 20 / 60 / 120 / 250 중 확보된 거래일 수 이하인 최댓값. 부족하면 `none` |
| `listing_note` | 참고 사항 | 예: `상장 3거래일째, 20일 지표 미산정` |

지표를 계산할 만큼의 기간이 없는 값은 빈 칸으로 두고, 이유를 `listing_note`에 적습니다. **0이나 다른 값으로 채우지 않습니다.** 0으로 채우면 AI가 "변화 없음"으로 읽기 때문입니다.

## 6. 수집 모드와 수집 상태

**수집 모드는 당일 모드와 기간 모드 두 가지이며, 둘 다 이미 성공적으로 받은 단위는 건너뜁니다.** 두 모드는 "받을 날짜 목록을 어떻게 정하느냐"만 다르고, 실제 수집 로직은 같은 코드를 씁니다. KRX와 KIS는 이 장을 따르고, DART는 9장의 별도 흐름을 따릅니다.

### 6.1 두 모드

| 모드 | 받을 날짜 목록 | 비고 |
| --- | --- | --- |
| 당일 | 보관 기간(시세 250일, 수급 120일) 안의 모든 거래일 중 아직 `success`가 아닌 날 + 마지막 장 마감일 | 하루 이틀 건너뛰어도 자동으로 채워짐 |
| 기간 | 사용자가 입력한 시작일\~종료일 사이의 거래일 중 `success`가 아닌 날 | 보관 기간 밖도 받을 수 있음. `--force`를 주면 `success`도 다시 받음 |

**"마지막 장 마감일"의 정의:** 실행 시각이 개장일 15:30 이후이면 오늘, 아니면 직전 개장일입니다. KRX 일별매매정보가 몇 시부터 당일 값을 주는지는 확인되지 않았으므로, 당일 요청이 빈 결과면 `empty`로 남기고 다음 실행 때 다시 받습니다.

### 6.2 처음 실행(빈 DB)일 때

DB에 아무것도 없으면 당일 모드가 곳 **초기 적재**가 됩니다. 시작 전에 "KRX 250거래일, KIS 수급 120거래일을 받습니다. 예상 약 N분"을 보여주고 확인을 받습니다. 중간에 끄어도 다음 실행 때 남은 단위부터 이어서 받습니다.

### 6.3 수집 단위

"이미 받았는가"는 아래 단위별로 판단합니다. 하나의 단위는 하나의 트랜잭션으로 저장되며, 저장이 끝난 뒤에야 `success`가 됩니다.

| 데이터 | 단위 (중복 판단 키) |
| --- | --- |
| KRX 일별매매정보 | (날짜, 시장) |
| KRX 종목기본정보 | (날짜, 시장) |
| KRX 지수 | (날짜, 시리즈) |
| KIS 종목별 수급 | (날짜, 종목) |
| KIS 시장별 수급 | (날짜, 시장) |
| KIS 주식기본조회 | (종목) — 최초 1회, 이후 신규 종목 |
| KIS 휴장일 | (조회일) — 하루 1회 |

KIS 수급은 한 번 호출로 여러 날짜가 오는 구조입니다. 응답에 들어온 모든 날짜를 저장하고, 그 날짜들을 한꺼번에 `success`로 표시합니다. 초기 적재는 종목별로 가장 오래된 빈 날짜까지 연속 조회(`tr_cont`)합니다.

### 6.4 수집 상태

| 상태 | 의미 | 다음 실행 때 |
| --- | --- | --- |
| `success` | 정상 수신·저장 완료 | 건너뜀 (`--force` 제외) |
| `provisional` | 저장했지만 확정값이 아닐 수 있음 (6.5) | 다시 받아 비교 |
| `empty` | 개장일인데 오류 없이 빈 결과가 옴 | 다시 받음. 3회 연속이면 상태 점검에 "재확인 필요"로 표시 |
| `failed` | 오류·타임아웃·한도 초과 | 다시 받음 |
| `holiday` | 휴장일로 확인됨 | 건너뜀 |
| `not_listed` | 그 날 상장되어 있지 않음 (상장 전·폐지 후) | 건너뜀 |

**개장일의 빈 결과를 절대 `success`로 처리하지 않습니다.** 오류 없이 빈 결과를 돌려주는 API가 있어, 이를 완료로 기록하면 빠진 날짜가 영원히 채워지지 않습니다.

### 6.5 수급의 잠정값과 확정값

KIS 문서에는 수급 확정 시각이 없습니다. 그래서 시각을 맞추려 하지 않고 구조로 해결합니다.

1. 실행일에 받은 "마지막 장 마감일" 수급은 `provisional`로 저장합니다.
2. 다음 실행 때 `provisional`인 날짜를 다시 받아 값을 비교합니다.
3. 값이 같으면 `success`로 바꿉니다. 다르면 새 값으로 갱신하고 `value_changes` 테이블에 이전 값·새 값·시각을 남긴 뒤 `success`로 바꿉니다.
4. 이 비교 기록이 쌓이면 몇 시 이후에 값이 더 바뀌지 않는지 나중에 알 수 있습니다. 그 시각이 확인되면 그 이후 실행분은 바로 `success`로 처리하도록 설정값만 바꿉니다.

브리핑 패키지에는 항목마다 잠정 여부를 표시합니다.

DART 테이블은 9장에 있습니다.

## 8. 브리핑 패키지 생성 (KRX+KIS)

**브리핑 패키지는 기준일 하루의 KRX·KIS 데이터를 요약 계산까지 마친 상태로 담은 xlsx 파일 하나입니다.** 수집과는 별도 메뉴(3번)로 실행하며, DB만 읽고 API는 호출하지 않습니다. DART 데이터는 넣지 않습니다.

### 8.1 원칙

| 원칙 | 내용 |
| --- | --- |
| 판단 없음 | 수익률·합계·배수 같은 계산만. "강세", "매수 후보", 점수, 순위는 만들지 않음 |
| 포함 조건 | 기준일의 KRX 매매정보가 `success`가 아니면 패키지를 만들지 않고 이유를 보여줌. KIS 수급이 비어 있으면 만들되, 해당 칸을 비우고 데이터 상태 시트에 표시 |
| 재현성 | 같은 기준일·같은 DB·같은 테마 버전이면 항상 같은 값. 안내 시트에 테마 버전과 계산 규칙 버전을 기록 |
| 과거 기준일 | 기준일을 과거로 주면 그 날까지의 데이터만 사용 (다음 날 값이 섞이지 않게) |
| 기계용 출력 | 같은 내용을 JSON으로도 출력할 수 있게 만들어 둠 (나중에 AI API 연동용) |

### 8.2 시트 구성

| 시트 | 행 단위 | 내용 |
| --- | --- | --- |
| `0_안내` | — | 기준일, 생성 시각, 대상 종목 수, 테마 버전, 단위표, 잠정값 여부, 컬럼 설명 |
| `1_시장` | 시장(코스피·코스닥) | 지수 종가·수익률(1·5·20·60일), 이동평균 대비 위치, 상승·하락 종목 수, 20일선 위 종목 비율, 거래대금 합계, 외국인·기관·개인 순매수(당일·5·20일) |
| `2_지수시리즈` | 지수 | KRX 시리즈 지수 전체의 수익률(1·5·20·60일). 업종지수 흐름 참고용 |
| `3_테마` | 테마 | 구성 종목 수, 수익률 중간값(1·5·20·60일), 상승 종목 비율, 거래대금 합계와 20일 평균 대비 배수, 외국인·기관 순매수 대금 합계(당일·5·20일), 순매수 종목 비율 |
| `4_종목` | 분석 대상 종목 전체 (약 2,500행) | 8.3의 컬럼 |
| `5_미분류` | 어느 테마에도 없는 종목 | `4_종목`과 같은 컬럼. 거래대금 배수 상위 50개, 외국인+기관 순매수 대금/시총 상위 50개를 각각 뽑아 합침 (기준 수는 설정값. 초기값 50으로 시작하고, 테마 마스터를 1개월 운영한 뒤 조정) |
| `6_데이터상태` | 항목 | 빈 날짜, `empty`·`failed` 단위, 잠정값 목록, `filter_conflict` 종목, 기업행동 의심 종목 |

`5_미분류`는 판단이 아니라 "테마 밖에서 움직임이 큰 종목"을 놓치지 않기 위한 목록입니다. 정기 점검 때 이 시트의 과거 기록을 되짚어 테마 편입을 검토합니다.

### 8.3 `4_종목` 컬럼

| 묶음 | 컬럼 |
| --- | --- |
| 식별 | code, name, market, themes (여러 개면 `;`로 구분), is\_admin, is\_halted |
| 신규 상장 | listed\_date, days\_since\_listing, is\_new\_listing, max\_window, listing\_note |
| 가격 | close, change\_rate\_pct, ret\_5d/20d/60d/120d/250d\_pct, high\_250d, low\_250d, pos\_250d\_pct (250일 범위 안 위치), gap\_ma5/20/60/120\_pct (이동평균 대비 이격) |
| 거래 | volume\_sh, value\_krw, value\_x\_ma5, value\_x\_ma20 (당일 거래대금 ÷ 직전 5·20일 평균), volume\_x\_ma20, mktcap\_krw |
| 수급 | frgn/orgn/prsn\_net\_qty 당일·5일·20일 합계, frgn/orgn/prsn\_net\_amt\_mil 당일·5일·20일 합계, frgn\_streak·orgn\_streak (연속 순매수·순매도 일수, 매도는 음수), frgn\_orgn\_net\_amt\_to\_mktcap\_bp\_5d (5일 외국인+기관 순매수 대금 ÷ 시총, bp) |
| 상태 | investor\_is\_provisional, corp\_action\_suspect, missing\_note |

**계산 규칙**

- n일 수익률 = (기준일 종가 ÷ n거래일 전 종가) − 1. 거래일은 달력 테이블 기준입니다.
- n일 합계·평균은 n거래일 자료가 **모두** 있을 때만 계산합니다. 하루라도 비면 빈 칸으로 두고 `missing_note`에 빠진 날짜를 적습니다.
- "직전 n일 평균"은 기준일을 제외한 앞의 n거래일입니다.

### 8.4 기업행동(액면분할 등) 처리

KRX 일별매매정보의 가격은 수정되지 않은 가격입니다. 그래서 액면분할·병합·무상증자가 있으면 실제로는 움직이지 않은 수익률이 찍힙니다.

1. 상장주식수(`LIST_SHRS`)가 전일 대비 바뀐 종목을 `corp_action_suspect`로 표시합니다.
2. 표시된 종목은 KIS 기간별시세(`FHKST03010100`)의 수정주가로 250일을 다시 받아 수익률·이동평균 계산에만 씁니다. 원본 가격은 그대로 둡니다.
3. 수정주가를 받지 못하면 그 종목의 수익률·이격 컬럼을 비우고 이유를 적습니다.

유상증자처럼 상장주식수는 바뀌지만 가격 수정이 필요 없는 경우도 표시됩니다. 표시는 "확인 대상"일 뿐 오류 판정이 아닙니다.

## 9. DART 주기 수집과 구글 시트 내보내기

**DART는 주 1회 또는 월 1회 수동으로 실행하고, 주요 계정만 추려 "기업·분기당 1행" CSV로 내보냅니다.** 이 CSV를 구글 시트에 올리고 Claude가 구글 시트 연결로 읽습니다. 전체 재무제표는 DB에만 둡니다.

### 9.1 수집 흐름

1. `corpCode.xml`을 받아 종목코드와 DART 기업코드 연결을 갱신합니다.
2. `list.json`으로 마지막 실행 이후에 접수된 정기보고서(분기·반기·사업보고서)의 접수번호와 접수일을 받습니다. 같은 기간의 전체 공시 목록(제목)도 함께 저장합니다.
3. 새로 나온 보고서마다 `fnlttSinglAcntAll.json`을 연결(`CFS`)로 조회합니다. 연결이 없는 회사는 상태 코드 `013`이 오므로 그때 별도(`OFS`)로 다시 조회합니다. `013`은 오류로 처리하지 않습니다 ([AlgoLab](https://algolab.co.kr/blog/dart-opendart-financial-statement-api-lag-2026)).
4. 주요 계정을 뽑고 분기 단독 값으로 환산한 뒤(9.3), 내보내기 CSV를 만듭니다.

**초기 적재는 며칠에 나눠서 합니다.** 3년치는 약 2,500개 기업 × 12개 보고서로 약 30,000회인데, DART 하루 한도는 약 20,000회입니다. 하루 사용량을 설정값(기본 18,000회)으로 제한하고, 다 쓰면 멈춘 뒤 다음 실행 때 이어서 받습니다. 남은 건수는 상태 점검에 표시합니다.

### 9.2 DART 테이블

| 테이블 | 기본키 | 주요 컬럼 |
| --- | --- | --- |
| `dart_corp` | corp\_code | stock\_code, corp\_name, modify\_date |
| `dart_filings` | rcept\_no | corp\_code, report\_nm, rcept\_dt, pblntf\_ty, is\_correction |
| `dart_fs_raw` | rcept\_no, fs\_div, sj\_div, account\_id, ord | account\_nm, thstrm\_amount, thstrm\_add\_amount, currency (응답 원문 그대로) |
| `dart_fs_quarter` | corp\_code, fiscal\_year, quarter, fs\_div | 주요 계정 분기 단독 값, 누적 값, rcept\_dt, calc\_note |

### 9.3 주요 계정과 환산 규칙

내보낼 계정: 매출액, 영업이익, 당기순이익, 자산총계, 부채총계, 자본총계, 영업활동현금흐름.

| 규칙 | 내용 |
| --- | --- |
| 계정 연결 | 표준 계정 ID(`account_id`)로만 연결. 이름이 비슷하다는 이유로 연결하지 않음. 못 찾으면 빈 칸 + `calc_note` |
| 당기 vs 누적 | `thstrm_amount`(당기)와 `thstrm_add_amount`(당기누적)는 다른 값. 보고서별로 어느 필드가 3개월 값인지 확인 후 사용 |
| 4분기 | DART에는 4분기 보고서가 없음. 손익·현금흐름 항목은 사업보고서 연간 값 − 3분기 누적 값 |
| 재무상태표 | 자산·부채·자본은 그 시점 잔액. 빼거나 더하지 않음 |
| 연결·별도 | 섞지 않음. 한 회사의 4개 분기가 같은 구분일 때만 TTM 계산 |
| 공개 시점 | 분기·반기보고서는 45일, 사업보고서는 90일 이내 제출. 모든 행에 접수일 `rcept_dt`를 붙여, 그 날 이전에는 쓸 수 없던 값임을 알 수 있게 함 |
| 정정 보고서 | 정정본이 오면 새 값으로 갱신하고 이전 값은 `value_changes`에 보관 |
| 금융업 | 은행·보험·증권은 매출액·영업이익 구조가 다름. 표준 ID가 없으면 빈 칸 + `금융업 구조` 표시 |

### 9.4 구글 시트용 내보내기

구글 시트는 스프레드시트 하나에 모든 탭을 합쳐 최대 1,000만 셀까지 담을 수 있습니다 ([Google Workspace 업데이트](https://workspaceupdates.googleblog.com/2022/03/ten-million-cells-google-sheets.html)). 그래서 전체 재무제표가 아니라 아래 형식만 내보냅니다.

| 파일 | 행 | 컬럼 | 규모 |
| --- | --- | --- | --- |
| `dart_financials_{기간}_{생성시각}.csv` | 기업 × 분기 | code, name, market, fiscal\_year, quarter, fs\_div, 7개 계정 분기 값, 손익 항목 TTM, rcept\_dt, calc\_note | 약 30,000행 × 20열 = 약 60만 셀 |
| `dart_filings_{기간}_{생성시각}.csv` | 공시 1건 | code, name, rcept\_dt, report\_nm, rcept\_no | 기간에 따라 다름 |

- 원 단위로 내보내고, 컬럼명에 `_krw`를 붙입니다.
- 업로드는 1단계에서는 사용자가 직접 합니다(구글 시트 메뉴의 파일 가져오기 → 시트 바꾸기). 구글 API 자동 업로드는 구글 클라우드 서비스 계정 설정이 필요하므로 2단계 선택 기능으로 둡니다.
- 공시 목록을 주간·월간으로만 받으므로, **당일 공시는 브리핑 때 Claude가 직접 찾아야 합니다.** 당일 공시 목록을 브리핑 패키지에 넣고 싶어지면 `list.json` 하루치(시장당 수 회 호출)만 당일 수집에 추가하면 됩니다.

## 10. 테마 마스터 파일

**테마는 사용자가 Claude와 함께 만든 CSV 하나(`themes/theme_master.csv`)로 관리하고, 프로그램은 읽기만 합니다.** 테마를 자동으로 만들거나 바꾸지 않습니다.

### 10.1 형식

```csv
theme,code,name,basis,added_date,note
HBM,000660,SK하이닉스,사업보고서 주요 제품,2026-11-20,
theme_example,000000,예시종목,연결 근거를 한 줄로,2026-11-20,필요하면 메모
```

| 컬럼 | 필수 | 설명 |
| --- | --- | --- |
| theme | 예 | 테마 이름 |
| code | 예 | 종목코드 6자리 (문자열. 엑셀이 앞의 0을 지우지 않도록 주의) |
| name | 아니오 | 사람이 읽기 위한 종목명. 프로그램은 code만 사용 |
| basis | 예 | 연결 근거 한 줄 |
| added\_date | 예 | 편입일 |
| note | 아니오 | 메모 |

한 종목이 여러 테마에 속해도 됩니다(줄을 여러 개 씁니다).

### 10.2 불러오기와 버전

1. 브리핑 패키지를 만들 때마다 CSV를 읽고 파일 내용의 해시를 계산합니다.
2. 해시가 지난 버전과 다르면 새 버전 번호를 매기고, 이전 CSV를 `themes/history/theme_master_v{번호}_{시각}.csv`로 복사해 둡니다.
3. 검사합니다: 없는 종목코드, 분석 대상에서 제외된 종목, 같은 (theme, code) 중복, 빈 필수 칸. 문제가 있는 줄은 빼고 데이터 상태 시트에 목록을 남깁니다.
4. CSV가 없으면 빈 양식을 만들고, 패키지는 테마 시트 없이 생성합니다.

### 10.3 정기 점검 지원

정기 점검 때 쓸 수 있도록 상태 점검 메뉴에 **"미분류 반복 등장 종목"** 내보내기를 둡니다. 지정한 기간(기본 최근 20거래일)에 `5_미분류` 목록에 오른 횟수를 종목별로 센 CSV입니다. 이 파일을 Claude에 올려 테마 편입을 검토하면 됩니다.

## 11. 호출 제한, 오류 처리, 로그, 백업

**모든 API 호출은 출처별 호출 조절기를 거치고, 실패는 멈추지 않고 기록한 뒤 다음 단위로 넘어갑니다.** 한 종목의 실패 때문에 나머지 2,499개가 멈추면 안 됩니다.

### 11.1 호출 제한

| 출처 | 알려진 한도 | 설정 기본값 | 초과 시 |
| --- | --- | --- | --- |
| KIS | 실전 초당 약 20건 (공식 문서에는 없고 커뮤니티 수치, [AlgoLab](https://algolab.co.kr/blog/kis-api-error-codes)) | 초당 15건 | `EGW00201` 응답 → 1초 쉬고 재시도, 연속되면 간격 2배 |
| KIS 휴장일 | 하루 1회 권고 (KIS 문서) | 하루 1회 | 캐시 사용 |
| KIS 토큰 | 발급 1분에 1회 | 캐시 우선 | 만료·무효 응답 시 1회만 재발급 |
| DART | 하루 약 20,000회 | 하루 18,000회 | `020` 응답 → 그 날 DART 수집 중단 |
| KRX | 미확인 | 초당 2건 | 오류 시 재시도 |

모든 한도는 코드가 아니라 설정 파일에 둡니다.

### 11.2 오류 처리

| 상황 | 처리 |
| --- | --- |
| 네트워크 오류·타임아웃 | 최대 3회 재시도 (대기 1·2·4초). 끝내 실패하면 `failed` |
| 응답은 왔지만 성공 코드가 아님 | 재시도하지 않고 `failed` + 응답 코드·메시지 기록 |
| 개장일인데 빈 결과 | `empty` (6장) |
| 응답 필드가 문서와 다름 (새 필드·빠진 필드) | 원본은 저장하고, 빠진 값은 `NULL`. 경고 로그 + 상태 점검에 표시 |
| 숫자가 아닌 값 (`-`, 빈 문자열, 쉼표) | 쉼표는 제거해 변환, 나머지는 `NULL`. 0으로 바꾸지 않음 |
| 인증 실패 (키 오류) | 즉시 중단하고 어느 키가 문제인지 표시 |
| 사용자가 중간에 종료 (Ctrl+C) | 진행 중인 단위만 버리고 종료. 다음 실행 때 이어서 진행 |

실행이 끝나면 화면에 요약을 보여줍니다: 출처별 성공·빈 결과·실패 건수, 걸린 시간, 재확인이 필요한 항목.

### 11.3 로그

- 실행마다 `logs/run_{시각}.log` 하나를 만듭니다.
- 기록 내용: 실행 모드, 대상 날짜, 호출 수, 오류 요약, 걸린 시간.
- API 키·토큰·앱시크릿은 로그에 적지 않습니다. 요청 헤더를 로그로 남기지 않습니다.
- 90일이 지난 로그는 자동 삭제합니다 (설정값).

### 11.4 백업

- 수집이 끝날 때마다 `backup/market_{시각}.sqlite` 스냅샷을 만듭니다. SQLite 백업 API를 써서 쓰기 중에도 안전하게 복사합니다.
- 최근 7개만 남기고 오래된 것은 지웁니다 (설정값).
- 원본 파일(`raw/`)이 남아 있으니 DB가 깨져도 원본에서 다시 만들 수 있게, `rebuild` 명령을 2단계 기능으로 둡니다.

KRX 종목기본정보만으로 판단합니다. 아래 세 조건을 모두 만족해야 분석 대상입니다.

| 조건 | 제외되는 것 |
| --- | --- |

### 16.2 받는 순서

1. **KRX** (`backfill krx`): `stk_bydd_trd`, `ksq_bydd_trd`, `kospi_dd_trd`, `kosdaq_dd_trd`를 2016-01-01부터 어제까지 평일마다 1회. 빈 응답은 `empty`(휴장 등, 성공 아님). 상장폐지 종목도 지우지 않음.
   - 보통주 판별: 종목기본정보를 과거 basDd로 부를 수 있으면 매월 첫 거래일 기준으로 받아 판별(`monthly_base_info`). 안 되면 현재 기준 정보 + 종목명·코드 규칙(우선주·스팩·리츠·인프라 제외, 보통주 단축코드 끝자리 0)으로 판별(`current_base_info+name_rule`). 판별 방법은 종목마다 기록.
   - 수정계수: (종가 − 전일대비) ≠ 그 종목의 직전 종가인 날을 기준가 조정일(액면분할·병합·무상증자 등)로 보고, 비율 = 기준가 ÷ 직전 종가. `adj_factor` = 그 날 이후 모든 비율의 곱(수정종가 = 종가 × adj_factor, 최근 가격 기준). 원시 가격은 그대로.
   - KRX 1년치(245거래일)를 받은 직후 DB 크기를 기록하고, `backfill status`에 10년 예상 크기를 표시.
2. **KIS 종목별 수급** (`backfill kis`): FHPTJ04160001, 시장 `J`, `FID_ORG_ADJ_PRC=0`. 대상은 KRX에 나온 보통주 전체(상장폐지 포함).
   - 우선순위: 기간 중 "시가총액 2,000억 원 이상 + 20일 평균 거래대금 50억 원 이상"을 한 번이라도 넘은 종목 먼저, 그다음 나머지.
   - 종목마다 마지막 거래일부터 과거로 30거래일씩. 15:40~23:59에만 실행하고, 시간이 끝나면 저장 후 멈춤.
   - 처음 실행할 때 상장폐지 종목 최대 5개로 응답 여부를 확인해 기록. 응답이 없어도 그 사실을 기록하고 계속 진행.
3. **DART** (`backfill dart`): 2015년 사업보고서부터 정기보고서 재무(정기공시 목록은 2016-01-01부터). 기존 DART 수집·분기 계산(14.4) 그대로. 오늘 쓸 수 있는 호출 = `DART_DAILY_LIMIT` − 정기 수집 DB의 오늘 사용량.

### 16.3 실행

- 명령줄만: `주식데이터수집기-명령.exe backfill krx | kis | dart | status | auto [--shutdown]`. GUI 버튼은 나중에.
- `backfill auto`: KRX가 남았으면 먼저 → 15:40~23:59이고 KIS가 남았으면 23:59까지 → DART(하루 한도 = `DART_DAILY_LIMIT` − 정기 수집 오늘 사용량 − 예비 `BACKFILL_DART_RESERVE`(기본 3,000, 정기 DART 수집용)). 한 단계가 오류로 멈춰도 다음 단계를 진행하고 실패 단계를 요약·보고서에 적음. `--shutdown`이면 끝난 뒤 `shutdown /s /t 60`으로 Windows 종료를 예약하고 60초 카운트다운, Ctrl+C면 `shutdown /a`로 취소.
- 정기 수집과 같은 잠금 파일을 써서 동시에 돌지 않음(동시 실행이면 안내만 내고 종료).
- Ctrl+C로 멈춰도 받은 단위는 저장되고 다음 실행 때 이어받음.
- 각 실행 끝에 `system/verify/backfill_<종류>_<시각>.md`: 받은 기간, 행 수, 빈 날짜, 실패 목록, 상장폐지 종목 수급 확인 결과.
- 호출 한도는 CLAUDE.md 그대로(KIS 초당 10건 균등 간격·한도 초과 시 절반 감속, KRX·DART는 설정값).

## 17. 백테스트 (추세추종 규칙 검증)

**16장에서 받은 `backtest.sqlite`로 추세추종 규칙을 계산만 합니다.** 주문·매매 API는 만들지 않습니다. 백테스트 DB는 읽기 전용으로만 열고 수집·백필 잠금 파일을 잡지 않으므로 백필이 도는 중에도 돌릴 수 있습니다. API 키가 없어도 실행되며 키 입력 창을 띄우지 않습니다. 쓰는 것은 결과 파일, 최근 데이터 합치기(sync), 내보내기 zip뿐입니다.

### 17.1 실행

| 명령 | 내용 |
| --- | --- |
| `backtest coverage [--db <경로>]` | 데이터 종류별 확보 기간·종목 수·진행률, 지금 돌릴 수 있는 변형 |
| `backtest run [A\|B\|C\|D\|all] [--db <경로>]` | 결과를 (DB 폴더)/results/<시각>/에 저장(summary.md, trades.csv, equity.csv), results/latest/에도 복사 |
| `backtest sync` | market.sqlite(읽기 전용)에서 백테스트 DB의 마지막 날짜 이후 확정값만 추가(잠정값 제외, 이미 있는 날짜·종목은 건너뜀). 보고서 system/verify/backtest_sync_<시각>.md. market.sqlite가 없으면 건너뜀 |
| `backtest export` | sync 후 SQLite 백업 API로 일관 복사 → 바탕화면 backtest_<마지막데이터일>.zip (DB 파일 하나만, 키·설정 없음) |

- DB 위치: 기본 데이터 폴더/backtest/backtest.sqlite. `--db` 또는 GUI [DB 파일 선택]으로 바꾸면 `config/settings.env`의 `BACKTEST_DB_PATH`에 저장.
- GUI [백테스트] 탭: 데이터 확보 현황, 변형 선택, [실행], 진행 막대, 결과 요약, [DB 파일 선택] [결과 폴더 열기] [최근 데이터 합치기] [업로드용 내보내기](합치기 자동 선행).

### 17.2 규칙 (모든 값은 `config/backtest.env`에서 변경)

| 항목 | 내용 |
| --- | --- |
| 기간·가격 | 2016-01-01 ~ 마지막 데이터일, 수정계수 적용 가격 |
| 생존 편향 | 날짜별로 그날 상장된 보통주만(상장폐지 포함). 보유 중 폐지되면 마지막 종가로 청산 |
| 거르기 | 시총 2,000억 원 이상, 20일 평균 거래대금 50억 원 이상 |
| 진입(장 마감 후) | 종가 > 60일선 > 120일선, 60일선 > 20일 전 60일선, 250일 범위 위치 80% 이상 |
| B | 20일 외국인+기관 순매수 합 / 시총이 그날 대상 중 상위 20%, 신호 당일 거래대금 ≥ 직전 20일 평균 × 1.5 |

### 17.3 변형 A 개선안과 공정 비교 (0.11.0)

변형 A의 큰 손실이 대부분 테마 급등주를 꼭대기에서 산 경우(2~7일 만에 −30~−44%)여서 선택지를 추가했습니다. 기본값은 기존 동작과 같습니다(`config/backtest.env`).

| 설정 | 값 | 내용 |
| --- | --- | --- |
| `RANK_BY` | value_surge(기본) / trend_quality | 신호가 넘칠 때 순서. trend_quality = 60일 수익률 ÷ (최근 60일 일간 수익률 표준편차 × √60), 높은 순 |
| `OVERHEAT_FILTER` | off(기본) / on | on이면 최근 20일 수익률 ≥ `OVERHEAT_RET20_PCT`(40) 또는 종가 ≥ 20일선 × (1 + `OVERHEAT_GAP20_PCT`/100)(25%)인 신호 제외 |
| `INDEX_FILTER_FOR_A` | off(기본) / on | D의 지수 필터를 A에도 적용 |
| `RANK_TIEBREAK` | value_surge(기본) / trend_quality | B·C·D에서 수급 점수가 같을 때 보조 순서 |

| 변형 | 내용 |
| --- | --- |
| A1 | A + trend_quality 순위 |
| A2 | A + 과열 제외 |
| A3 | A + 지수 필터 |
| A4 | A + 위 셋 모두 |
| A_sameB / A4_sameB | A·A4 규칙을 B가 실제로 계산된 종목·날짜에만 적용 (A_sameB와 B의 차이 = 수급 효과, A와 A_sameB의 차이 = 종목 범위 효과) |

- `backtest run all`은 A, A1~A4, B, C, D, A_sameB, A4_sameB를 모두 계산합니다(각각 진입 ①~④ × 청산 (가)(나)). 민감도는 _sameB를 뺀 변형만.
- 요약 추가: 거래당 기대값(= 승률×평균수익 + (1−승률)×평균손실, 비용 반영 후), 공정 비교 표, 변형별 손실 상위 10건(진입 직전 20일 수익률 포함), 연도별 수익률에 A1~A4 열.

### 17.4 종목 조건 효과를 시장과 분리 (0.12.0)
- 유니버스: 수집기와 같은 기준(SECUGRP_NM=주권, KIND=보통주, 스팩·기업인수목적·리츠·우선주 제외, 기본정보 없으면 종목명·코드 규칙). 제외 사유별 개수를 coverage와 summary에 표시.
- `BACKDROP_INDEX_FILTER=on|off`(기본 on): 지수 필터를 모든 변형에 공통 적용. summary 맨 위 "배경 설정"에 표시.
- 거래마다 같은 기간 시장지수 수익률(`index_ret_pct`)과 초과수익(`excess_pct` = 거래 수익률 − 지수 수익률). summary에 평균 초과수익, 초과수익 승률.
- `backtest signals`(GUI [신호 분석]): 매매 규칙 없이 기본 신호(필터 + A 진입 조건, 같은 종목 `SIGNAL_GAP_DAYS`=20거래일 내 중복 제외)의 다음날 시가 기준 5/20/60일 수익률·초과수익을 과열, 거래대금 급증, 추세 품질, 수급, 재무, 시장 배경(120일선)별로 나눠 n, 평균/중앙값 초과수익, 승률, t값, 최상위−최하위 차이를 개발(~2022)/검증(2023~)로 표시. 30건 미만은 "표본 부족". 결과 signals.md, signals.csv.
- `backtest run --random N`(기본 100): 같은 후보군에서 같은 개수를 무작위로 골라 같은 매매 규칙으로 N회(①(가) 조합, 시드 `RANDOM_SEED`=42 고정). CAGR·MDD 분포와 전략의 백분위.
